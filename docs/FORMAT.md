# `.vip` file format

The canonical save format for viper songs. Plain text, line-oriented,
whitespace-tolerant, diffable, greppable, `:%s`-able.

## Design principles

1. **Round-trip lossless.** In-memory `Song` ↔ `.vip` text must be exactly
   reversible. If you parse then serialize, you get byte-identical output
   (modulo comments). This is non-negotiable.
2. **Human-writable.** A composer with a text editor and no viper install
   should be able to author a valid `.vip` by hand.
3. **LLM-friendly.** The format is regular enough that a language model
   can emit valid `.vip` given the grammar and two examples.
4. **Forgiving parser, strict writer.** Readers accept variable whitespace,
   optional fields, mixed case, trailing commas. Writers always emit the
   canonical form below.
5. **Order-independent where possible.** `@song` header can appear after
   `@phrase` blocks. Phrases can appear in any order; the `@song` order
   array decides playback.

## Grammar

```
file        := (line)*
line        := comment | blank | directive | data_row
comment     := '#' .* '\n'
blank       := '\n'
directive   := '@' ident (ws key_value)* '\n'
data_row    := hex2 ws cell (ws cell)* '\n'
cell        := note | '---'
note        := letter accidental octave   # e.g. C-4, D#3, F-5
accidental  := '-' | '#'
key_value   := ident '=' value
```

Notes are always 3 chars wide. `---` means empty. Sharps only (no flats,
matches every tracker from ProTracker forward). Octaves 0–9.

Rows carry five cells: `PU1 PU2 TRI NOI DPCM`. Files with four cells
per row still load; the DPCM column is empty. On the DPCM column the
note picks a sample: `C-4` = 00, `C#4` = 01, … (built-in bank: kick,
snare, hat; `@dpcm` overrides). On NOI the pitch selects one of the 16
noise periods (C-2 and below = deepest rumble, C-7 and above = hiss).

## Canonical example

```vip
# song.vip — generated by :gen "four-on-the-floor 140bpm"
@song  bpm=140  steps=16  order=[00,01,00,02]  loop=01
@meta  title="Four Floors"  artist="viper"  license="MIT"
@driver  bin=driver/build/driver.bin  sym=driver/build/driver.sym  expansion=none
@dpcm 00  name=kick   path=samples/kick.dmc

@phrase 00
  # step   PU1   PU2   TRI   NOI
  00       C-4   ---   C-3   G-2
  04       D#4   ---   G-3   ---
  08       G-4   C-5   C-4   G-2
  12       F-4   ---   G-3   ---

@phrase 01
  00       ---   E-4   C-3   G-2
  02       ---   G-4   ---   ---
  04       ---   C-5   G-3   G-2
  ...

@phrase 02
  00       ---   ---   ---   G-2
  04       ---   ---   ---   G-2
  08       ---   ---   ---   G-2
  12       ---   ---   ---   G-2

@instr 00  voice=pulse25  a=02  d=08  s=0C  r=06
@instr 01  voice=triangle a=00  d=00  s=0F  r=04
@instr 02  voice=noise    a=00  d=04  s=00  r=00

# Optional modulation bindings (stage 12)
@bind sprite mario.0 scale = tri.env * 0.5 + 1.0
@bind sprite mario.0 hue   = pu1.pitch % 360
```

## Cell columns

For v0 the cell is just a note. For v0.2 (stage 3+), a cell is:

```
C-4:01:0F:A04
```

where the colon-separated fields are `note:instr:volume:effect`. Any field
may be `--` (or `---` for note) to mean empty/inherit. Whitespace between
cells is arbitrary; alignment is writer's choice.

## Song structure

Two ways to sequence phrases. The flat form lives on `@song`:

```
@song  bpm=140  order=[00,01,00,02]  loop=01
```

The structured form (Stage 23) groups phrases into **chains** and
sequences chains in an **arrangement**. Rows under `@chain` are hex phrase
indices, rows under `@arrangement` are hex chain indices; `loop=` names the
arrangement slot playback returns to after the last one.

```
@chain 00  name="verse"
  00 01 00 01
@chain 01  name="chorus"
  02 03
@arrangement  loop=01
  00 01 01 00
```

Playback flattens arrangement → chains → phrases into one order list, so
the NSF compiler and every exporter see exactly what `order=` would have
said. A file with an arrangement never writes `order=` (and `order=` is
ignored with a warning if both appear). Chains may be empty; every chain
is written so arrangement indices stay stable.

Two per-song timing tweaks sit beside them:

```
@length  pu1=16  pu2=16  tri=12  noi=8  dpcm=16
@groove  swing=120
@groove
  -120 120 -120 120 -120 120 -120 120 -120 120 -120 120 -120 120 -120 120
```

`@length` is polymeter: a channel shorter than 16 steps reads
`cells[step % length]` and cycles inside every phrase. It is honored by
the synth engine, `:bounce`, and the NSF compiler (which unrolls it).
`@groove` shifts each 16th by a signed number of samples on the synth
step clock; `swing=N` is shorthand for `-N +N -N +N …`. The NSF driver's
row clock is fixed, so groove is synth-only and the compiler warns when
it is set. Both directives are omitted from the canonical output when
they hold the defaults.

## Canonical writer output

- Indent data rows with 2 spaces.
- Align columns to the widest cell in that column within the phrase.
- Always include a comment header row (`# step   PU1   PU2   TRI   NOI`)
  at the top of each phrase.
- Empty rows between phrases (one blank line).
- Sort directives in this order: `@song`, `@meta`, `@driver`, `@dpcm`,
  `@phrase` (by index), `@chain` (by index), `@arrangement`, `@groove`,
  `@length`, `@instr` (by index).
- Hex values lowercase in step indices, uppercase in volume/effect fields
  (tracker convention).
- One trailing newline at EOF.

## Reserved `@` directives

| directive | purpose                                    | stage |
|-----------|--------------------------------------------|-------|
| `@song`   | global song parameters; `order=[..]` + `loop=NN` = song mode | 3.5 / 16 |
| `@phrase` | phrase definition, followed by data rows   | 3.5   |
| `@chain`  | `NN [name=".."]` + rows of phrase indices — see [Song structure](#song-structure) | 23 |
| `@arrangement` | `[loop=NN]` + rows of chain indices; decides playback order | 23 |
| `@length` | `pu1=16 pu2=16 tri=16 noi=16 dpcm=16` per-channel wrap length (polymeter) | 23 |
| `@groove` | `swing=N`, or a row of 16 signed sample offsets (synth engine only) | 23 |
| `@instr`  | instrument definition                      | 3     |
| `@scene`  | named snapshot of chain state              | 7     |
| `@bind`   | modulation binding                         | 12    |
| `@sprite` | sprite sheet reference + palette           | 11    |
| `@meta`   | free-form key=value metadata (author, etc) | any   |
| `@driver` | NSF driver binary/symbol map + expansion flag | 18    |
| `@dpcm`   | `NN name=.. path=..` DPCM sample for note C-4+NN | 18    |

## Effect column

`CPP`: one command letter and two hex digits. The internal synth ignores
effects; the NSF driver implements them (Stage 18):

| fx | meaning |
|----|---------|
| `Rxx` | retrigger the note every `xx` frames (`R00` off) |
| `Dxx` | duty: 0 = 12.5 %, 1 = 25 %, 2 = 50 %, 3 = 75 % (NOI: mode bit) |
| `Sxx` | portamento speed in period units per frame; while set, new notes slide (`S00` off) |
| `Vdr` | vibrato, depth `d` (0–F) and rate `r` (0–F); `V00` off |
| `Axy` | arpeggio root / +x / +y semitones per frame; `A00` off |
| `E00` | restart the volume envelope without retriggering |

Effect state persists on the channel until changed.

## Parser error handling

- Unknown `@directive` → warn, skip the directive and its data block.
- Malformed cell → warn, treat as `---`.
- Out-of-range note → warn, clamp to 0–127.
- Duplicate `@phrase <n>` → last one wins; warn.
- Never fatal except on malformed UTF-8 or unreadable file.

The philosophy: **a partially broken `.vip` should still load and play
what it can.** Composers will hand-edit these. Being strict is hostile.

## Why not TOML/YAML/JSON?

- **TOML**: no good way to express tabular step data without ugly arrays.
- **YAML**: whitespace-sensitive in ways that conflict with tracker-style
  alignment; implementation complexity.
- **JSON**: no comments, no alignment, hostile to hand-editing.

The tracker grid is the natural representation. Formalize what composers
already write on graph paper, don't force-fit a config language.

## Validation

`viper --check song.vip` parses and reports issues without launching the
TUI. Useful for CI on a repo of `.vip` files, and for LLM output
validation before `:gen` accepts generated content.
